# تصميم النظام v2

## 1. حالة الوثيقة

- **الحالة:** مسودة تصميم معتمدة مبدئيًا للمراجعة قبل التنفيذ.
- **الإصدار:** v2.0
- **التاريخ:** 2026-10-07
- **النطاق:** إعادة بناء النظام على `main` مع إبقاء النسخة الحالية قابلة للرجوع في فرعي `legacy/smart-poster` و`docs/current-system-baseline`.
- **قاعدة مهمة:** لا يبدأ تنفيذ الكود أو تغيير قاعدة البيانات قبل مراجعة هذه الوثيقة واعتمادها.

---

## 2. الرؤية الجديدة

النظام ليس مجرد أداة لإعادة نشر الأخبار، بل منصة مرنة لإدارة وتوزيع **محتوى متنوع** من Telegram إلى عدة قنوات أهداف، وفق فئات وقواعد مستقلة.

> يملك المستخدم الرئيسي عدة أهداف نشر. لكل هدف مصادره ومساراته وقواعده وتوقيعه وطريقة نشره. ويمكن للمصدر الواحد أن يخدم أكثر من هدف، مع إعدادات مختلفة في كل هدف.

أمثلة للفئات الممكنة:

- أخبار.
- رياضة.
- عروض ومنتجات.
- تعليم.
- وظائف.
- تقنية.
- محتوى ترفيهي.
- إعلانات.
- أي فئة يحددها المستخدم.

الفئة ليست قيمة ثابتة داخل النظام؛ هي بيانات قابلة للإنشاء والتعديل، ويمكن استخدامها في التصفية والتصنيف والتوجيه.

## 3. القرارات المعتمدة

| القرار | المعتمد |
|---|---|
| المستخدم الأول | مالك رئيسي واحد |
| التوسع المستقبلي | دعم عدة ملاك/عملاء مع عزل البيانات والصلاحيات |
| معنى الهدف | قناة Telegram ينشر فيها النظام |
| تعدد الأهداف | نعم، وكل هدف مستقل في إعداداته |
| استخدام المصدر | يمكن ربط المصدر بأكثر من هدف |
| حساب القراءة | حساب Telegram مستخدم واحد في البداية |
| النشر | مباشر أو طابور مجدول حسب إعداد الهدف/المسار |
| المحتوى القديم | لا يحفظ افتراضيًا؛ يحفظ فقط ما يدخل مسار الجدولة أو المعالجة المطلوبة |
| الوسائط | تخزين مؤقت بمدة احتفاظ قابلة للضبط ثم حذف تلقائي |
| التكرار | منع تكرار على مستوى الهدف، مع بصمة للرسالة والمحتوى |
| الذكاء الاصطناعي | مؤجل إلى مرحلة لاحقة، وليس شرطًا للنواة |
| الإدارة | لوحة ويب مستقلة + Telegram Mini App + بوت تحكم مختصر |
| قاعدة البيانات | PostgreSQL |
| الطوابير | تبدأ بطابور داخل التطبيق عند الحاجة، مع تصميم قابل لإضافة Redis/worker لاحقًا |
| المعمارية | Modular Monolith أولًا، قابل للفصل إلى خدمات مستقلة عند زيادة الحمل |
| الفرع الحالي | محفوظ كمرجع، و`main` مخصص لإعادة البناء |

## 4. المصطلحات الأساسية

### 4.1 الحساب Account

المالك أو العميل الذي يملك إعدادات وبيانات معزولة. في النسخة الأولى يوجد حساب مالك واحد، لكن كل الجداول الجديدة يجب أن تتضمن `account_id` أو ترتبط به بطريقة واضحة.

### 4.2 المشروع Project

تجميع منطقي لأهداف ومصادر وفئة تشغيل واحدة. يمكن أن يمثل نشاطًا أو علامة أو مجال محتوى.

مثال: مشروع `أخبار اليمن` أو مشروع `عروض المتاجر`.

### 4.3 الهدف Destination

قناة Telegram التي تستقبل المنشورات. قد يحتوي المشروع على هدف واحد أو عدة أهداف.

### 4.4 المصدر Source

قناة أو مجموعة أو حساب Telegram يقرأ منه حساب المستخدم.

### 4.5 مسار المصدر Source Route

العلاقة بين مصدر وهدف. هذا هو الكيان الأهم في التصميم، لأنه يحمل القواعد الخاصة باستخدام مصدر معين داخل هدف معين.

مثال:

```text
مصدر واحد
├── هدف الأخبار: تنظيف سياسي + نشر مباشر + توقيع الأخبار
└── هدف العروض: إبقاء السعر + نشر كل 30 دقيقة + توقيع العروض
```

### 4.6 ملف القواعد Profile

مجموعة إعدادات قابلة لإعادة الاستخدام، مثل:

- ملف توقيع.
- ملف تنظيف وتحويل.
- ملف فلترة.
- ملف منع تكرار.
- ملف جدولة.

### 4.7 عنصر المحتوى Content Item

نسخة داخلية من منشور Telegram عندما يحتاج النظام إلى حفظه للجدولة أو المراجعة أو إعادة المحاولة. لا يحفظ كل المحتوى تلقائيًا.

### 4.8 مهمة النشر Publish Job

طلب نشر محدد لعنصر محتوى إلى هدف معين، وله حالة ومحاولات ووقت تنفيذ.

## 5. نطاق النسخة الأولى الجديدة V2-MVP

### داخل النطاق

1. PostgreSQL بدل SQLite.
2. مستخدم رئيسي واحد مع نموذج بيانات جاهز للتعدد.
3. عدة مشاريع أو أهداف.
4. عدة مصادر لكل هدف.
5. ربط مصدر واحد بأكثر من هدف.
6. إعدادات مستقلة لكل Source Route.
7. نشر مباشر للرسائل الجديدة.
8. منع تكرار داخل كل هدف.
9. توقيع مستقل لكل هدف أو مسار.
10. فلاتر مستقلة لكل مصدر داخل كل هدف.
11. تصنيفات مرنة وقواعد تصنيف يدوية.
12. حفظ انتقائي للمحتوى الذي يدخل الجدولة أو يحتاج إعادة محاولة.
13. طابور نشر داخلي واضح الحالات.
14. تخزين وسائط مؤقت بمدة احتفاظ.
15. لوحة ويب مستقلة للوظائف الأساسية.
16. Telegram Mini App للوصول السريع.
17. بوت تحكم مختصر للتنبيهات والأوامر السريعة.
18. سجل تدقيق وتشخيص بدون تسريب أسرار أو كلمات مرور.
19. ترحيل إعدادات ومصادر النسخة الحالية إلى PostgreSQL.

### خارج النطاق في V2-MVP

- عدة حسابات Telegram للقراءة.
- الذكاء الاصطناعي والتلخيص وإعادة الصياغة.
- مراجعة بشرية متقدمة متعددة المراحل.
- نظام دفع واشتراكات.
- تطبيق جوال أصلي.
- Microservices مستقلة بالكامل.
- أرشفة كل الرسائل بلا حدود.
- تحليل تشابه دلالي متقدم.

## 6. حالات الاستخدام الأساسية

### UC-01: إنشاء هدف

1. يفتح المالك لوحة الإدارة.
2. ينشئ هدفًا جديدًا.
3. يحدد اسم الهدف وقناة Telegram.
4. يحدد الفئة أو الفئات المرتبطة به.
5. يحدد طريقة النشر والتوقيع ومنع التكرار.
6. يحفظ الهدف في حالة متوقف حتى يكتمل الاختبار.

### UC-02: ربط مصدر بهدف

1. يختار المالك مصدرًا موجودًا أو يضيف مصدرًا جديدًا.
2. يختار الهدف.
3. ينشئ Source Route.
4. يضبط فلترة المصدر وطريقة النشر والتوقيع.
5. يفعّل المسار بعد نجاح اختبار الوصول.

### UC-03: النشر المباشر

```text
Telegram NewMessage
→ التحقق من المصدر
→ إنشاء Ingestion Event
→ تطبيع المحتوى
→ حساب البصمات
→ تطبيق قواعد Source Route
→ فحص التكرار
→ إنشاء Publish Job فوري
→ النشر
→ تسجيل النتيجة
```

### UC-04: الجدولة من المحتوى المحفوظ

1. يفعّل المالك وضع الحفظ أو الجدولة للمسار.
2. تصل الرسالة أو يتم استيرادها ضمن النطاق المسموح.
3. يحفظ النظام النص والبيانات والوسائط مؤقتًا.
4. توضع الرسالة في طابور الهدف.
5. يوزع Scheduler الرسائل حسب السرعة والوقت والقواعد.
6. ينشر Publisher الرسالة.
7. يحذف الوسائط بعد انتهاء مدة الاحتفاظ، مع إبقاء سجل مختصر.

### UC-05: استخدام مصدر في هدفين

كل هدف يطبق قواعده الخاصة ولا يفترض أن تكون معالجة المصدر واحدة للجميع.

### UC-06: إيقاف هدف دون إيقاف بقية الأهداف

إيقاف هدف يمنع إنشاء أو تنفيذ مهام نشره فقط، ولا يوقف قراءة المصدر إذا كان مستخدمًا في مسارات أخرى.

## 7. نموذج النشر

### 7.1 النشر المباشر

- أقل زمن ممكن بين وصول الرسالة والنشر.
- لا يحتاج حفظًا دائمًا للمحتوى بعد نجاح النشر.
- يحتفظ بسجل نتيجة وبصمة لمنع التكرار.
- في حالة الفشل، يحفظ الحد الأدنى اللازم لإعادة المحاولة وفق سياسة الهدف.

### 7.2 النشر من الطابور

- لا يرسل مباشرة.
- يحتاج إلى حفظ المحتوى والوسائط حتى يتم التنفيذ.
- يدعم ترتيبًا وأولوية ومعدل نشر.
- يراعي FloodWait وحدود Telegram.
- يملك حالات واضحة:

```text
queued → processing → publishing → published
                         ├→ retry_wait
                         ├→ failed
                         └→ cancelled
```

### 7.3 توزيع الطابور

الإعدادات المقترحة لكل هدف:

- أقصى عدد رسائل في الدقيقة.
- الفاصل الأدنى بين الرسائل.
- ترتيب FIFO أو حسب الأولوية.
- نافذة زمنية مسموحة.
- السماح أو المنع للتزاحم بين المصادر.
- إعادة المحاولة وعددها.
- تصرف الرسائل القديمة بعد انتهاء صلاحيتها.

---

## 8. قواعد الفلترة والتصنيف

### 8.1 ترتيب تطبيق القواعد

```text
استقبال
→ تطبيع
→ فلترة المصدر
→ فلترة الهدف
→ تصنيف
→ إزالة التكرار
→ تحويل النص والوسائط
→ إنشاء مهمة النشر
```

يمكن تعديل الترتيب لاحقًا إذا أثبتت الاختبارات أن إزالة التكرار قبل التنظيف أفضل، لكن يجب أن يكون الترتيب موحدًا ومُسجلًا.

### 8.2 الفلترة

لكل Source Route:

- كلمات تضمين.
- كلمات استبعاد.
- أنواع وسائط مسموحة.
- حد أدنى/أقصى لطول النص.
- روابط مسموحة أو محذوفة.
- حقوق المصدر التي تزال.
- رموز أو قوالب توقيع مصدرية قابلة للضبط.
- مصدر أو كاتب أو وسم Telegram.

### 8.3 التصنيف

في V2-MVP:

- تصنيفات ينشئها المستخدم.
- قواعد مبنية على كلمات ووسوم ومصدر.
- إمكانية تعيين تصنيف افتراضي لكل مصدر.
- إمكانية تصنيف الرسالة إلى أكثر من فئة.

في مرحلة لاحقة يمكن إضافة مصنف AI خلف واجهة مستقلة دون تغيير Pipeline الأساسي.

## 9. منع التكرار

### المستوى الأول: رسالة Telegram

مفتاح منطقي:

```text
source_id + telegram_message_id
```

### المستوى الثاني: محتوى متطابق

بصمة على المحتوى المطبع:

```text
sha256(normalized_text + media_identity)
```

### المستوى الثالث: التكرار داخل الهدف

لا يمنع نشر نفس المحتوى في أهداف مختلفة، لكنه يمنع تكراره داخل نفس الهدف خلال نافذة يحددها المستخدم.

إعدادات منع التكرار لكل هدف:

- مدة النافذة.
- الاعتماد على تطابق الرسالة فقط.
- الاعتماد على تطابق النص والوسائط.
- سياسة التعامل مع الرسالة المتطابقة: تجاهل أو تحديث أو ربط بالمصدر الأصلي.

التحليل الدلالي المتقدم مؤجل.

## 10. التخزين والاحتفاظ

### 10.1 قاعدة البيانات

PostgreSQL تخزن:

- الإعدادات والعلاقات.
- البيانات الوصفية للمحتوى.
- الحالات والمؤشرات.
- المهام والمحاولات.
- البصمات.
- سجل التدقيق.

### 10.2 الوسائط

الوسائط لا تحفظ داخل PostgreSQL. تستخدم طبقة Object Storage قابلة للتبديل:

- S3 أو Cloudflare R2 في الإنتاج.
- تخزين محلي مؤقت في التطوير.

كل ملف له:

- مفتاح تخزين.
- نوع وحجم.
- checksum.
- تاريخ انتهاء.
- حالة الحذف.

### 10.3 سياسة الاحتفاظ

إعدادات قابلة للتحديد:

- مدة حفظ المحتوى المجدول.
- مدة حفظ الوسائط بعد النشر.
- مدة حفظ السجلات التشغيلية.
- حذف تلقائي بعملية تنظيف دورية.

القيمة الافتراضية المقترحة للوسائط: 7 أيام، وتكون قابلة للتغيير لكل مشروع أو هدف.

## 12. المعمارية التشغيلية

نبدأ بـ **Modular Monolith** مع عمليات منفصلة عند الحاجة:

```text
apps/
├── api              # REST API ولوحة الويب
├── bot              # Telegram Bot وMini App bridge
├── worker           # استقبال ومعالجة ونشر في البداية
└── scheduler        # موزع الطوابير والمهام المجدولة

modules/
├── identity
├── projects
├── destinations
├── sources
├── telegram
├── ingestion
├── content
├── rules
├── deduplication
├── classification
├── scheduling
├── publishing
├── storage
├── audit
└── notifications
```

في البداية يمكن تشغيل `worker` و`scheduler` داخل عملية واحدة لتقليل التعقيد، لكن الحدود البرمجية بينهما تكون مستقلة.

### التدفق العام

```text
Telegram User Session
        ↓
Ingestion Adapter
        ↓
Content Pipeline
        ↓
Route Resolver
        ↓
Deduplication
        ↓
Direct Publisher أو Publish Queue
        ↓
Telegram Bot API
        ↓
PostgreSQL + Object Storage + Audit
```

### قابلية التوسع لاحقًا

عند زيادة الحمل يمكن فصل:

- Ingestion Worker.
- Processing Worker.
- Publishing Worker.
- Scheduler.

ويضاف Redis أو نظام طوابير خارجي دون تغيير منطق المجال.

## 13. لوحة الإدارة

### 13.1 الويب المستقل

لوحة ويب كاملة، ويمكن فتحها من أي متصفح، مع تسجيل دخول آمن.

الصفحات الأساسية:

```text
Dashboard
Projects
Destinations
Sources
Source Routes
Content Queue
Scheduled Posts
Published Posts
Filters
Classifications
Branding
Telegram Session
System Health
Audit Logs
Settings
```

### 13.2 Telegram Mini App

واجهة سريعة داخل Telegram للمهام المتكررة:

- عرض الأهداف.
- تشغيل وإيقاف هدف.
- عرض الطابور.
- إعادة محاولة مهمة.
- إضافة أو تعطيل مصدر.
- عرض الأخطاء.
- فتح لوحة الويب الكاملة.

### 13.3 بوت التحكم

يبقى للبوت دور مختصر:

- `/status`
- `/projects`
- `/destination`
- `/queue`
- `/run`
- `/pause`
- `/errors`
- رابط لوحة الإدارة

لا نعتمد على Reply Keyboard لإدارة كل إعدادات النظام بعد V2.

## 14. الصلاحيات المستقبلية

حتى مع مالك واحد في البداية، يصمم النظام بالأدوار التالية:

- `owner`: كل الصلاحيات.
- `admin`: إدارة المشاريع والمصادر والأهداف.
- `editor`: إدارة المحتوى والطوابير دون إعدادات الحساب.
- `operator`: تشغيل وإيقاف ومتابعة الأخطاء.
- `viewer`: قراءة الحالة والتقارير فقط.

كل طلب API يجب أن يتحقق من:

1. هوية المستخدم.
2. الحساب الذي ينتمي إليه.
3. المشروع/الهدف المطلوب.
4. الصلاحية اللازمة.

## 15. ترحيل النظام الحالي

لن نحذف النظام الحالي أو نعيد استخدام بنيته قسرًا.

### ما يحفظ

- فرع `legacy/smart-poster`.
- فرع `docs/current-system-baseline`.
- ملف جلسة Telegram في بيئة التشغيل.
- نسخة SQLite الحالية قبل الترحيل.
- التوقيع الحالي والمصادر الحالية.

### Importer مطلوب

يبني أداة ترحيل تقوم بـ:

1. قراءة جدول `settings`.
2. إنشاء Account وProject وDestination.
3. إنشاء Telegram Account واحد.
4. تحويل `sources` إلى Sources وSource Routes.
5. تحويل الفلاتر والتوقيع إلى Profiles.
6. حفظ `baseline_message_id` في `source_checkpoints`.
7. تنفيذ فحص تطابق قبل اعتماد الترحيل.

لا تهاجر الرسائل القديمة لأن النسخة الحالية لا تحفظ محتوى المنشورات أصلًا.

## 17. معايير الجودة

### وظيفية

- لا تنشر الرسالة في هدف غير مرتبط بها.
- نفس المصدر يمكن أن يعمل بقواعد مختلفة لكل هدف.
- إيقاف هدف لا يوقف بقية الأهداف.
- لا يتكرر المحتوى داخل الهدف وفق السياسة.
- الرسائل المباشرة لا تدخل الجدولة إلا إذا طلب الإعداد ذلك.
- المحتوى المجدول لا يفقد وسيطه قبل التنفيذ.
- حذف الوسائط يتم بعد انتهاء retention فقط.

### تشغيلية

- فشل مصدر أو هدف لا يسقط النظام كاملًا.
- كل مهمة لها حالة قابلة للتتبع.
- إعادة المحاولة لا تنشئ تكرارًا.
- Restart لا يفقد الطابور أو checkpoints.
- PostgreSQL هي المصدر المركزي للحالة.

### أمنية

- عزل بيانات الحسابات.
- عدم تسجيل محتوى حساس أو جلسات.
- تشفير/حماية أسرار Telegram.
- صلاحيات API على مستوى الهدف والمشروع.
- حماية Mini App وWeb App من انتحال المستخدم.

### أداء

- النشر المباشر لا ينتظر Scheduler.
- معالجة المصادر لا تكون تسلسلية عالميًا.
- حدود الإرسال تطبق لكل هدف أو Bot API policy.
- الاستعلامات الأساسية تستخدم فهارس مناسبة.

## 18. المخاطر والقرارات المفتوحة

### 18.1 مصدر واحد مع عدة أهداف

تم اعتماد دعم ذلك، ويتطلب Source Route مستقلًا وعدم تخزين إعدادات المعالجة على Source نفسه.

### 18.2 جدولة المحتوى القديم

لا يمكن جدولة محتوى لم يتم حفظه. لذلك يجب أن يكون لكل Route سياسة واضحة:

- مباشر فقط.
- حفظ للجدولة.
- حفظ وإعادة محاولة.

### 18.3 الوسائط الكبيرة

الفيديوهات قد ترفع التكلفة وتضغط التخزين. يجب دعم حد الحجم وسياسة حذف وفشل واضحة.

### 18.4 حدود Telegram

يجب أن يملك Publisher طابورًا وحدودًا وإعادة محاولة، لا أن يعتمد على `sleep` ثابت فقط.

### 18.5 الجلسة الواحدة

الحساب الواحد قد لا يستطيع الوصول لكل المصادر. التصميم يسمح بإضافة Telegram Accounts لاحقًا، لكن V2-MVP يبدأ بحساب واحد.

### 18.6 PostgreSQL وRedis

PostgreSQL إلزامية في النظام الجديد. Redis ليس إلزاميًا في أول مرحلة إذا كان طابور PostgreSQL كافيًا، لكنه سيكون خيارًا طبيعيًا عند زيادة الحمل.

### 18.7 التوقيع والتنظيف

قواعد التنظيف يجب أن تكون Profiles قابلة للضبط، لا قيمًا ثابتة داخل الكود كما في النسخة الحالية.

## 19. قرار التنفيذ الحالي

بعد اعتماد هذه الوثيقة، تكون الخطوة البرمجية الأولى فقط:

> بناء أساس V2 وقاعدة PostgreSQL وDomain Model وmigrations، دون ربط النشر الحقيقي أو حذف النظام الحالي.

ثم نمر عبر بوابة اختبار قبل إضافة Telegram أو لوحة الويب.

لا يبدأ التنفيذ قبل مراجعة أي تغييرات على:

- تعريف المشروع والهدف والمسار.
- طريقة المصادقة في الويب وMini App.
- شكل الترحيل من SQLite.

## 20. خلاصة التصميم

النظام الجديد سيكون منصة متعددة الأهداف والقواعد، وليس Relay أحادي الإعدادات.

الهيكل المنطقي النهائي:

```text
Account
└── Projects
    ├── Destinations
    │   ├── Publishing Mode
    │   ├── Branding Profile
    │   ├── Deduplication Profile
    │   └── Schedule Profile
    │
    └── Source Routes
        ├── Source
        ├── Route-specific Filters
        ├── Route-specific Transform
        ├── Route-specific Classification
        └── Route-specific Retention

Telegram Ingestion
→ Content Pipeline
→ Route Resolution
→ Deduplication
→ Direct Publish أو Queue
→ Destination Channel
```

بهذا التصميم نستطيع البدء بمالك واحد وحساب Telegram واحد، ثم التوسع لاحقًا إلى عدة ملاك وحسابات وعملاء دون إعادة بناء جوهر النظام.
